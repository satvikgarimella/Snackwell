The thread

1/7 · 228 characters · Attach 01-sm-architecture.png

Snackwell can do matrix math now 😎 Since the last update, I’ve added FP32 multiply/add/subtract and a 4×4 systolic array, then connected the tensor unit to the SM with a TMUL instruction. Here’s how the data moves through it 👇

2/7 · 241 characters

First came FP32: FMUL, FADD, and FSUB. These take multiple cycles, so the SM has to remember the issuing warp, destination register, and active lanes until the result returns. Dependent instructions wait; independent work can keep running.

3/7 · 236 characters · Attach tensor-flow.mp4

Then came the systolic array. A values move right. B values move down. Each of the 16 processing elements keeps one output value and accumulates four products. The animation shows the operands moving and the partial sums building up 👇

4/7 · 245 characters · Attach 02-processing-element.png

Inside each PE: an FP32 multiplier, an adder, and a local accumulator. This version rounds after both operations, so the MAC is non-fused. The whole array advances when every PE finishes. Ten logical steps here take more than ten clock cycles.

5/7 · 237 characters · Attach 03-tmul-registers.png

The array now runs through the real SM: TMUL R8, R0, R4 A lives in R0–R3, B in R4–R7, and C goes to R8–R11. Each register holds one row across four lanes. All four destination registers stay reserved until the last result row commits.

6/7 · 225 characters · Attach 05-test-results.png

Then I tested the full path. 35/35 testbenches pass. The SM tensor suite checks 185 matrix cases / 2,960 outputs, plus overlapping registers, all 16 lane masks, competing warps, divergence, reset, and writeback backpressure.

7/7 · 256 characters

Snackwell now has FP32 execution and its first integrated tensor unit. It’s still a fixed 4×4 design with one tensor job at a time, verified in simulation. Next: shared-memory conflict replay, a small assembler, and the first reusable kernels. More soon!
